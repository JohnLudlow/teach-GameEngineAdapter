Lesson 11: TUI Capability Negotiation

Let consumer code choose an appropriate experience from advertised adapter capabilities.

Mission connection: A terminal adapter is not a reduced 2D engine. Capability negotiation lets the game preserve meaningful interaction when sprites, meshes, mouse input, color, or advanced terminal features are unavailable.

Capabilities describe the adapter, not the desired UI

A capability is an observable fact about what an adapter can reliably provide. The consumer reads those facts and selects a compatible presentation or behavior. It must not issue an unsupported request and hope the adapter silently approximates it.

Capability Possible value Consumer response
2D sprites Unavailable in the TUI Use labels, lists, and panels instead of attempting sprite rendering.
Mouse click Available in the first TUI scope Enable click interaction while retaining keyboard access.
Color May vary by terminal Ensure information remains understandable without color alone.
Viewport layout Available through the adapter Use the shared control tree; do not calculate terminal output directly.

Absence is normal, not exceptional

Capability negotiation happens before an optional feature is used. A TUI that reports no 2D or 3D rendering support is valid. It is not expected to simulate those features, throw on every frame, or make the game unusable. The consumer selects a text-oriented path instead.

if adapter.Supports2D:
    showMapSprites()
else:
    showMapSummaryPanel()

if adapter.SupportsMouseClick:
    allowPointerSelection()

always:
    allowKeyboardSelection()

The important distinction is between required capabilities, without which the application cannot run, and optional capabilities, for which the consumer must provide a fallback. The adapter does not decide which presentation matters most to a particular game.

Do not use capabilities as a proxy for state

A capability answers whether an adapter can provide a feature. It does not answer whether a control is enabled, whether its data is present, or whether the terminal is currently too small. Those are current UI-state or layout outcomes and can change during a session.

Example: mouse click support may be advertised by the adapter, yet a button can still be disabled. Conversely, a compact layout can be active even though the adapter supports wide layouts. Keep these questions separate in the contract.

Capability contracts must be stable and testable

Each advertised capability needs a precise definition. If an adapter reports mouse-click support, it must deliver click behavior according to the agreed focus and activation rules. If it reports a feature as unavailable, consumer fallback behavior should be testable with a headless adapter configured without that capability.

Given: an adapter without 2D sprite support
When: the game creates its map view
Then: it creates a text summary panel instead of requesting sprites

Given: an adapter with mouse-click support
When: the user clicks an enabled button
Then: focus moves to the button and its action is invoked once

Retrieval practice

Answer each question from memory, then expand it to check your answer.

Who decides how to respond when an optional capability is unavailable?

The consumer. It chooses a compatible fallback presentation or behavior; the adapter advertises what it can provide.

Why is a TUI without 2D or 3D support still a valid adapter?

The game can select a text-oriented presentation. The adapter is valid when it accurately advertises its capabilities and supports its promised contract.

Is a disabled button evidence that the adapter lacks mouse-click support?

No. Mouse-click support is an adapter capability; a button's enabled state is current consumer-owned UI state.

What must an adapter do after advertising a capability?

It must reliably provide the precisely defined behavior represented by that capability, so consumers can test and rely on it.

Decision recorded

The first-release TUI advertises no 2D or 3D rendering support, supports mouse clicks, and always supports keyboard interaction. Color is not guaranteed, so consumer UI must not depend on color alone to convey information.
