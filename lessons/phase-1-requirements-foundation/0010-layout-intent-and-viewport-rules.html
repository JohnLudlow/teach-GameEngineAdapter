Lesson 10: Layout Intent and Viewport Rules

Keep terminal rendering adapter-owned while leaving room for consumer-selected responsive layouts.

Mission connection: The first-release TUI owns layout, but future games may need different arrangements at different terminal sizes. The contract must preserve that option without putting cursor movement, screen clearing, or terminal measurements into consumer code.

Three responsibilities, not one

Responsibility Owner Example
UI state and domain meaning Consumer The Economy tab is selected and its list contains three cities.
Responsive layout intent Consumer, if it opts in later At narrow widths, show city details below the list rather than beside it.
Measurement, placement, and terminal drawing Adapter Determine character-cell bounds, clip safely, and write terminal output.

The second responsibility is deliberately about intent, not rendering. A consumer may choose an arrangement using a viewport category or dimensions, but it does not calculate terminal coordinates or render controls itself.

What a future viewport rule may decide

A viewport rule chooses among semantic layout variants. It can select which regions are visible, their order, and their broad relationship. The adapter still determines whether the chosen variant fits, applies spacing, and renders the result.

Wide viewport:
[ city list            ][ selected city details ]

Narrow viewport:
[ city list                                ]
[ selected city details                    ]

Too small for either:
[ Terminal is too small: minimum 40 × 12 ]

These are three layout outcomes for the same UI state. Selection, focus, and the underlying city data do not change because the terminal became narrower.

What a viewport rule must not decide

  • Terminal cursor coordinates, clearing behavior, colors, or output buffering.
  • Whether a key press activates a control or where focus moves.
  • Fallback state that invents a different selected item, checked value, or domain choice.
  • Whether the adapter redraws after a visible change.

Those responsibilities must remain uniform across layout variants. Otherwise, each responsive arrangement becomes a separate interaction model and deterministic headless testing is lost.

Prefer a narrow extension seam

The first release needs no viewport-rule API. When one is added, it should accept only layout-relevant information and produce a declarative layout choice or specification. Do not expose a terminal object or callback that renders directly.

Design boundary: a callback such as Render(Terminal terminal) would reintroduce engine-specific rendering into consumer code. A rule such as ChooseLayout(viewport) preserves the adapter boundary because the adapter still owns rendering.

Test the invariant, not terminal output

A headless test can model wide, narrow, and too-small viewports. It should verify the selected layout outcome and that focus, selection, and values are preserved across the changes. It need not assert exact cursor positions or ANSI sequences.

Given: "City A" is selected and "Build Farm" is focused
When: the viewport changes from wide to narrow
Then: the narrow layout variant is selected
And: "City A" remains selected
And: "Build Farm" remains focused

Given: the viewport is too small for every supported variant
When: the next frame renders
Then: the minimum-size fallback is visible
And: no consumer-owned UI state changes

Retrieval practice

Answer each question from memory, then expand it to check your answer.

Who owns terminal measurement and drawing when a consumer supplies a viewport rule?

The adapter. The consumer may supply layout intent, but it does not measure, position, or render terminal controls.

What may change between wide and narrow layout variants?

Visible regions, their order, and their broad arrangement may change. The consumer-owned UI and application state must not change merely because the viewport changed.

Why should a future viewport-rule API avoid a terminal rendering callback?

It would make consumer code engine-specific and break the adapter boundary. The adapter must remain responsible for terminal rendering.

What should a headless responsive-layout test assert?

It should assert the chosen layout outcome and preservation of focus, selection, and values, rather than terminal cursor positions or escape sequences.

Decision recorded

The viewport-rule API shape is deferred until a real consumer requires it. The shared contract preserves the adapter boundary and extension point, but defines neither named variants nor region constraints prematurely.
