Lesson 5: Focus and Activation Baseline

Define deterministic focus transitions before deciding each control’s action semantics.

Mission connection: The failed prototype’s unpredictable Tab behavior becomes a small set of explicit, testable focus rules. This gives a future TUI adapter a portable interaction target rather than library-specific behavior.

The agreed focus model

Checkboxes, lists, buttons, tab controls, and panels or groups are eligible for focus traversal. Tab and Shift+Tab must traverse enabled eligible controls deterministically.

Situation Required behavior Reason it is observable
Tab or Shift+Tab Move through enabled eligible controls in a deterministic order. The same control tree and input sequence must produce the same focused control.
Panel or group encountered Enter the container by moving focus to its first enabled eligible child. The container does not become a dead-end focus stop.
Focused control disabled Retain focus, but prevent activation. Re-enabling the control restores activation without a focus move.
Focused control removed Move focus to the next enabled eligible control, wrapping when necessary. The control tree has a defined recovery result rather than an arbitrary focus loss.

Activation and pointer behavior

Space and Enter activate the focused interactive control. Clicking an enabled interactive control first moves focus to that control, then applies that control’s action. This separates shared focus behavior from the action that differs by control.

1. Hit test: identify the enabled interactive control under the click.
2. Focus: move focus to that control.
3. Activate: apply the control-specific action once.
4. Render: show the updated focus and control state in the next visible UI.
Important distinction: a disabled focused control remains focused but cannot activate. A removed focused control does not remain in the tree, so the focus-recovery rule applies. Treating those cases as identical would lose the agreed behavior.

What this baseline does not decide

Focus and activation are shared interaction rules. They do not decide each control’s domain-specific action. The next design step must define these semantics:

Control Action still to define
Checkbox Its checked-state transition and whether both Space and Enter toggle it.
List Selection movement, selection confirmation, and how selection is rendered.
Button The command or callback it invokes and its post-activation visible state.
Tab control How keyboard and click input select a page and which descendants are then eligible.

Test the transitions, not a terminal library

A headless focus test should operate on a fixed control tree and assert the resulting focused identifier and activation outcome. It should not assert cursor escape sequences or library objects. That keeps the test tied to the shared behavioral contract.

Given: focus is on "sound-enabled"
When: "sound-enabled" becomes disabled
Then: focus remains "sound-enabled"
And: Space does not activate it

Given: focus is on "sound-enabled"
When: "sound-enabled" is removed
Then: focus moves to the next enabled eligible control

Retrieval practice

Answer each question from memory, then expand it to check your answer.

What happens when traversal reaches a panel or group?

Focus enters the container by moving to its first enabled eligible child; the container is not itself a dead-end focus stop.

What is the difference between disabling and removing the focused control?

A disabled control retains focus but cannot activate. A removed control transfers focus to the next enabled eligible control, wrapping if needed.

What is the required sequence for clicking an enabled interactive control?

Identify the clicked control, move focus to it, apply its action once, and render the resulting state.

Why should focus tests avoid terminal-library objects and escape sequences?

The test should prove the portable focus and activation contract, not the incidental implementation of one terminal library.
