Lesson 4: First-Release TUI Requirement Baseline

Separate the requirements already agreed from interaction rules that still need a decision.

Mission connection: You now have a bounded first release instead of a terminal UI with unlimited features. That turns the failed prototype’s symptoms into a design target while keeping implementation blocked on the remaining contract decisions.

Agreed first-release scope

The first usable TUI must provide labels, checkboxes, lists, panels, buttons, and tab controls. It must support mouse clicks, but mouse move and scroll are outside this first release.

Requirement area Agreed baseline Acceptance evidence
Control scope Label, checkbox, list, panel, button, and tab control Each control appears in an end-to-end UI scenario
Mouse Click support is included; move and scroll are excluded Click behavior is covered for every interactive included control
Focus Tab and Shift+Tab cycle deterministically through enabled controls A fixed control tree always produces the same focus-transition sequence
Redraw Full redraws are allowed when output remains visually stable Idle and normal-interaction scenarios show no visible redraw flicker

Scope is not interaction semantics

Knowing that a button and a tab control exist does not yet define what they do. A requirement needs the input, the state transition, and the observable output. The same applies to a mouse click: it tells us the input channel, not the hit-testing, focus, or activation rule.

Input: name the key or click that triggers the behavior.
Target: identify how the focused or clicked control is selected.
Transition: state the control or focus change.
Output: state what the next visible UI must show.
Test: define the deterministic assertion for the sequence.

For example, “a button supports click” is scope. “Clicking an enabled button invokes its assigned action once and updates the next rendered state” is an observable behavior. Whether that same click also moves focus remains a separate decision.

Decisions still required before a shared contract

These are not implementation details. They determine the public behavior that a future UI contract must represent.

Decision Why it matters
Focusable controls Defines the exact traversal set for Tab and Shift+Tab.
Keyboard and click mappings Defines how each interactive control changes state or invokes an action.
Pointer-to-focus rule Defines whether a click moves focus before or after it activates a control.
Disabled and removed controls Defines how focus recovery remains deterministic when the UI changes.
Resize outcome Defines what must be redrawn and what happens when content no longer fits.
Implementation gate: Do not select a terminal UI library or add members to IUserInterfaceProvider until these behaviors are agreed. The current provider remains empty, so it cannot make any of them portable.

Retrieval practice

Answer each question from memory, then expand it to check your answer.

Which mouse behavior is included in the first release?

Mouse clicks are included. Mouse move and scroll are explicitly outside the first-release scope.

What must Tab and Shift+Tab do?

They must cycle deterministically through enabled controls. The exact focusable set still needs to be defined.

Does permitting full redraws define the redraw implementation?

No. It defines an observable constraint: redraws must remain visually stable during idle and normal interaction.

Why is “supports click” incomplete for a button?

It does not specify the target-selection rule, action or state transition, visible output, or deterministic test.
