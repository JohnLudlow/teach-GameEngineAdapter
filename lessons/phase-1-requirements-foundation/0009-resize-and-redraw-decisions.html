Lesson 9: Resize and Redraw Decisions

Define what the terminal adapter observes, recalculates, and makes visible when its viewport or UI state changes.

Mission connection: The prior prototype flickered because it treated terminal output like an always-redrawn game scene. A reliable TUI needs observable resize and redraw rules before a terminal library can supply its own defaults.

Resize is a viewport change, not a domain change

A terminal resize changes the space available to the adapter. It does not change the game or application state. The adapter must learn the new size, recalculate layout from the same consumer-owned UI definition, and render the result within the new viewport.

Before resize: viewport 120 columns × 40 rows
Consumer state: Economy tab selected, "Build Farm" button focused

After resize: viewport 80 columns × 24 rows
Consumer state: Economy tab selected, "Build Farm" button focused
Adapter work: recompute layout and render the same state in 80 × 24

Resize must not silently alter selection, focus, checked values, or application state merely to fit a smaller terminal. If a control cannot fit, that is a layout-policy question, not permission to invent a different interaction state.

A redraw makes the latest state visible

Invalidation means the current terminal image is no longer an accurate representation of the UI state. A redraw renders that latest state. The shared contract should describe the observable trigger and visibility point, not require a dirty-region or double-buffer implementation.

Change Does the display need a redraw? Reason
Terminal viewport is resized Yes The layout may no longer fit the available space.
Focus, selection, checkbox value, or visible tab changes Yes The user-visible representation changed.
Consumer replaces data displayed by a control Yes The content is stale.
No UI state or viewport change No Redrawing an identical idle screen adds work and risks flicker without a visible benefit.

Frame timing must be explicit

The adapter may collect several changes before its next render opportunity, then draw the latest complete state once. This coalescing is an implementation detail. The contract decision is when callers can rely on the update being visible: immediately after dispatch, by the next frame, or only after an explicit render request.

Do not confuse correctness with frequency: rendering every frame can be correct only if the output remains stable. It is not required merely because the game loop has frames. A TUI should redraw when its visible state is invalidated and must remain visually stable while idle.

Three decisions the contract still needs

  1. Resize notification: Does the consumer receive the new viewport dimensions, or does the adapter use them internally to lay out a consumer-supplied control tree?
  2. Too-small viewport: When minimum layout requirements do not fit, should the adapter render a deterministic compact or clipped state, or an explicit "terminal too small" view?
  3. Visibility boundary: Is a valid UI change guaranteed visible by the next frame, or must the consumer explicitly request a render?

Agreed first-release baseline

The adapter owns layout using the current viewport, renders an explicit minimum-size fallback view, and guarantees a redraw by the next frame after a viewport or visible UI-state change. This keeps sizing details out of game logic, avoids accidental clipping, and gives tests a clear visibility boundary.

The shared contract must remain extensible for a consumer to supply viewport-size rules for alternative layouts in a later release. The first release does not need that feature, but its API must not assume that one adapter-owned layout policy can be the only policy forever.

Given: a valid UI is rendered at 120 × 40
When: the terminal changes to 80 × 24
Then: the adapter recomputes layout using 80 × 24
And: focus and selection are unchanged
And: the resulting view is visible by the next frame

Given: a valid UI cannot meet its minimum size at 20 × 5
When: the next frame renders
Then: an explicit minimum-size fallback is visible
And: the adapter does not invent a new selection or application state

Retrieval practice

Answer each question from memory, then expand it to check your answer.

What must a resize preserve?

Consumer-owned UI and application state, including focus and selection. The adapter recalculates layout for the new viewport.

When does a TUI need a redraw?

When the viewport or a user-visible UI state changes. It need not redraw an unchanged idle screen.

What is the difference between invalidation and redraw?

Invalidation identifies that the displayed image is stale; a redraw makes the latest state visible.

Why is a "redraw every game frame" rule insufficient?

It does not define whether output is stable, when a state change is visible, or how the adapter responds to a resize. It can also cause unnecessary work and flicker.
