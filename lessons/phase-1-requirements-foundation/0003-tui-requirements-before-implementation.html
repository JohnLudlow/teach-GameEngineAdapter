Lesson 3: TUI Requirements Before Implementation

Convert the discarded prototype’s failures into decisions that can be observed and tested.

Mission connection: The goal is not to select a terminal library or write an adapter yet. The goal is to make a smaller TUI scope whose behavior can be agreed, implemented, and tested.

Symptoms are evidence, not requirements

The prototype flickered, controls were not interactive, mouse support was unclear, and Tab focus was unpredictable. Each symptom identifies a behavior that the next design must make observable. It does not by itself choose an implementation.

Observed symptom Requirement to define Evidence for acceptance
Visible flickering When output is redrawn and how resize changes it A repeatable idle and interaction scenario produces stable output
Checkboxes did not work Which controls are included and how activation changes their state Each included control has a keyboard-driven state-change test
No apparent mouse support Whether pointer click, move, and scroll are in scope Mouse behavior is tested, or the first release explicitly excludes it
Unpredictable Tab focus Initial focus, Tab and Shift+Tab order, and disabled-control behavior A fixed control tree always yields the same focus transitions

Write observable requirements

An observable requirement states the trigger, the visible result, and any relevant boundary. It avoids implementation words such as “use double buffering” until the behavior is agreed.

1. Name the user action: for example, pressing Tab, pressing Space, clicking, or resizing the terminal.
2. State the expected outcome: for example, focus moves to the next eligible control or a checked value changes.
3. State the boundary: identify what is excluded or what happens when the terminal cannot provide the capability.
4. State the test: describe the input and assertion that would prove the behavior.

For example, “the controls should work” is not testable. A requirement such as “Space toggles the focused enabled checkbox, and the next render contains its new value” identifies a trigger, result, and test. It still leaves the control set and focus rules to be agreed.

The current contract boundary

IInputProvider polls key state, mouse-button state, and mouse position. That is not a UI event model. IUserInterfaceProvider currently has no members, so it does not define controls, focus, layout, invalidation, or UI events across adapters.

Design gate: Do not add a shared provider member because a terminal library happens to expose it. First identify a portable, observable behavior that the game needs from every relevant adapter.

Decisions required for the first usable TUI

These are decisions for the next collaborative requirements session, not assumptions this lesson makes:

Decision Minimum useful definition
Control set The exact controls included in the first release, such as a label, checkbox, list, or panel.
Keyboard behavior The commands each included control accepts and the order in which focus moves.
Mouse scope Supported and tested, or explicitly excluded from the first release.
Redraw and resize When output becomes visible and the expected result of a terminal size change.
Capabilities What the adapter advertises and how consumers behave when a capability is unavailable.

Retrieval practice

Answer each question from memory, then expand it to check your answer.

Why is “the controls should work” not a useful requirement?

It does not identify a control, trigger, expected state change, or test. An observable requirement must describe behavior that can be checked.

What must the design decide about mouse input?

Whether mouse behavior is supported and tested, or explicitly excluded from the first release.

Why does the current IUserInterfaceProvider not solve focus or checkbox behavior?

It has no members, so it defines no portable controls, focus model, UI events, layout, or invalidation behavior.

When should a shared TUI contract be proposed?

After the required behavior is observable and portable across the adapters that need it, rather than because a chosen terminal library exposes an API.
