Lesson 13: Shared UI Contract Shape

Translate the agreed TUI behavior into a minimal boundary that neither owns game state nor exposes terminal details.

Mission connection: IUserInterfaceProvider is currently empty. The next contract must make focus, selection, layout, and events testable without becoming a terminal-widget wrapper or a second game-state model.

Four directions across the boundary

Direction What crosses the boundary Example
Consumer to adapter: definition What the UI means and contains. A list with stable item identifiers, labels, and its consumer-supplied initial selection.
Consumer to adapter: update Changed application-owned data or control state. Replace a city's list entries or disable a button.
Adapter to consumer: event A user interaction or adapter-observed transition. List item city-b selected, checkbox value changed, or button activated.
Adapter internal work Measurement, terminal input handling, layout, and drawing. Translate a mouse click into a stable control identifier and redraw.

Only the first three directions need shared contract types. The fourth remains adapter implementation detail.

Definitions describe current intent, not mutable widgets

A control definition should use stable identifiers and declarative properties. It says that a button exists, has a label, is enabled, and represents a consumer-defined action. It must not expose a terminal library's button instance, event loop, cursor coordinate, or callback registration method.

Button definition:
  id: "build-farm"
  label: "Build Farm"
  enabled: true

Adapter event:
  kind: Activated
  controlId: "build-farm"

The consumer receives the event, decides its domain effect, updates its own state, and supplies a new definition or update. The adapter does not directly create a farm because a terminal button was activated.

A consumer update can intentionally produce an adapter event when the contract defines that transition. For example, applying a selection update may report the resulting selection so another consumer component can update a details panel. Such events are explicit behavior, not an automatic echo of every update.

Updates replace state; events report transitions

Consumer-to-adapter updates represent the latest intended UI state. Adapter-to-consumer events represent something that happened. Do not overload one message type for both directions: an event such as Selected("city-b") is not a request for the adapter to choose that selection.

Ownership rule: selection and focus are observable adapter state, but their application significance belongs to the consumer. The adapter reports transitions; it does not persist domain decisions or silently fabricate invalid initial state.

Commands need no public terminal-input API

A production adapter obtains key and pointer input from its platform. Headless tests need a deterministic way to dispatch equivalent semantic input, such as Tab, Down, Activate, or Click(control identifier). That seam should serve testing without requiring consumer code to know how a terminal library produces raw input events.

Headless test:
  dispatch(Tab)
  advanceFrame()
  assert focusedControlId == "city-list"

Terminal adapter:
  receives physical Tab key
  translates it to the same semantic navigation behavior

Start with the smallest public vocabulary

The first contract should name only the controls and outcomes already agreed: labels, checkboxes, lists, panels/groups, buttons, and tab controls; IDs; enabled state; selection; events; viewport/layout outcome; and frame visibility. Keep layout rules and terminal capabilities declarative. Defer controls or callbacks without a tested consumer scenario.

Retrieval practice

Answer each question from memory, then expand it to check your answer.

What are the three kinds of information that cross the shared UI boundary?

Consumer-supplied definitions, consumer-supplied updates, and adapter-reported events. Terminal implementation work remains internal.

Why should a control definition use stable identifiers rather than terminal-widget objects?

Identifiers describe engine-independent intent and remain testable across adapters. Widget objects leak a terminal library into consumer code.

How do an update and an event differ?

An update expresses the consumer's latest intended UI state; an event reports a user interaction or observed adapter transition.

Why should headless tests dispatch semantic commands rather than raw terminal input?

Semantic commands make behavior deterministic and adapter-independent while the production adapter remains responsible for translating platform input.

Decision recorded

The MVP accepts immutable whole-tree updates because they preserve consumer ownership and make invalid-state validation deterministic. Stable control identifiers and the contract boundary must permit incremental updates later, when large UI trees make replacement unnecessarily expensive.
