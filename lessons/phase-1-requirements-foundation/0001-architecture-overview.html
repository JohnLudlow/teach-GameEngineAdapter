Lesson 1: Architecture Overview

Understanding the adapter pattern, provider model, and how GameEngineAdapter decouples game logic from engines

📖 Lesson Goal: Understand the architectural patterns that make GameEngineAdapter work. By the end, you'll be able to explain why it's organized the way it is, and what each layer does.

The Problem: Coupling Game Logic to Engine-Specific Code

Imagine you're writing a 4X game in MonoGame. You write:

// Game logic tied to MonoGame
class GameSimulation
{
    private SpriteBatch _spriteBatch;  // MonoGame-specific
    private Keyboard _keyboard;         // MonoGame-specific

    public void Update()
    {
        // Your game logic is now hardcoded to MonoGame APIs
        _spriteBatch.Draw(...);
    }
}

Now you want to run the same game on Stride, or in a Terminal UI, or in a Headless test environment. Problem: your entire game logic is entangled with MonoGame. You have to rewrite everything.

GameEngineAdapter solves this by inverting the dependency: your game logic depends on abstract contracts (interfaces), not concrete engine code. Each engine implements the contracts. Game logic stays portable.

The Solution: The Adapter Pattern

GameEngineAdapter uses the Adapter Pattern (also called Hexagonal Architecture or Ports and Adapters):

    ┌──────────────────────────────────┐
    │        GAME LOGIC                │
    │      (Your 4X Game)              │
    └──────────────┬───────────────────┘
                   │
            ┌──────▼─────────┐
            │ IEngineAdapter │
            └──────┬─────────┘
                   │
        ┌──────────┼──────────┐
        │          │          │
    ┌───▼──┐  ┌────▼────┐  ┌──▼────────┐
    │Render│  │ Input   │  │  Audio    │
    │      │  │         │  │           │
    │ Prov │  │ Prov    │  │ Player    │
    └──────┘  └─────────┘  └───────────┘
        │          │            │
    ┌───┴──────────┴────────────┴──┐
    │     (Each adapter provides   │
    │     the providers and        │
    │     advertises capabilities) │
    │                              │
    │   • MonoGame                 │
    │   • Stride                   │
    │   • TUI                      │
    │   • Headless                 │
    └──────────────────────────────┘
Key insight: Game logic sits at the center, depending only on abstract IEngineAdapter and its providers. The current Headless adapter and future engine adapters implement those contracts. Game logic does not need to reference a concrete engine.

The Three Architectural Layers

Layer Contains Location Dependencies
Core Contracts Interfaces (IEngineAdapter, IRenderProvider, etc.) and DTOs (SpriteDrawDto, etc.) GameEngineAdapter.Core/ None (no external deps)
Game Logic Your 4X game simulation Your project Depends on GameEngineAdapter.Core
Adapters Engine-specific implementations (MonoGame, TUI, Headless, etc.) GameEngineAdapter.Headless/, future adapters Depends on GameEngineAdapter.Core and engine libraries

The flow is always one direction: Game Logic → Contracts ← Adapters. Game logic never knows about adapters. Adapters depend on contracts.

The Central Contract: IEngineAdapter

Every engine adapter implements IEngineAdapter. It looks roughly like this:

public interface IEngineAdapter : IDisposable
{
    // Describe what this adapter can do
    EngineCapabilities Capabilities { get; }

    // Lifecycle
    Task InitializeAsync(EngineConfig config, CancellationToken ct = default);
    Task ShutdownAsync(CancellationToken ct = default);

    // Get providers for rendering, input, audio, assets, UI
    IRenderProvider RenderProvider { get; }
    IInputProvider InputProvider { get; }
    IAudioPlayer AudioPlayer { get; }
    IAssetProvider AssetProvider { get; }
    IUserInterfaceProvider UserInterfaceProvider { get; }

}

Each adapter must provide:

  • Capabilities — What features and resource limits does this adapter advertise?
  • Lifecycle methods — Initialize and shut down the adapter.
  • Providers — Objects your game uses to render, receive input, play audio, manage assets, show UI

The Provider Model: Separation of Concerns

Rather than cramming everything into one mega-interface, GameEngineAdapter splits functionality into focused providers:

Provider What It Does Example Usage
IRenderProvider Submit draw commands (sprites, meshes, text) renderProvider.SubmitSprite(in sprite)
IInputProvider Poll key state, mouse-button state, and mouse position inputProvider.IsKeyDown("Space")
IAudioPlayer Play, stop, and control audio audioPlayer.StartPlayback(soundId)
IAssetProvider Cache, query, and unload assets through an asset loader assetProvider.GetAsset(assetId)
IUserInterfaceProvider Reserved for adapter-owned UI operations; it currently has no members No current operation

Why separate providers? Each provider owns a focused responsibility. The adapter exposes capability metadata so consumers can adapt when an optional feature is unavailable. The empty UI provider does not yet define portable controls, panels, or buttons.

Capability Negotiation: Knowing What the Engine Can Do

Not all adapters support the same rendering, audio, and rich-UI features. How does a consumer adapt?

Every adapter reports its EngineCapabilities:

public readonly record struct EngineCapabilities(
    bool Supports2D,
    bool Supports3D,
    bool SupportsShaders,
    bool SupportsAudio,
    bool SupportsRichUI,
    string ContractVersion,
    IReadOnlyList<string> SupportedTextureFormats,
    int MaxTextureSize,
    int MaxAudioChannels);

Your game logic checks capabilities and adapts:

void SubmitSpriteIfSupported(
    IEngineAdapter adapter,
    in SpriteDrawDto sprite)
{
    if (adapter.Capabilities.Supports2D)
    {
        adapter.RenderProvider.SubmitSprite(in sprite);
    }
}

This way, the same game logic can adapt to different engines without conditional compilation or runtime errors.

A Concrete Example: The Frame Cycle (How HeadlessAdapter Works)

Let's trace the explicit render lifecycle used by the headless deterministic runner:

1. Game calls BeginFrame(in camera)
Returns a FrameScope — a disposable that marks the frame boundary.
2. Game submits draw commands
Call SubmitSprite, SubmitText, and SubmitMesh as needed.
3. Game calls EndFrame()
This explicitly ends the active render frame.
4. Game calls Present()
This explicitly presents the completed frame. Disposing FrameScope is a no-op and does not replace either call.
✅ Frame complete. Recorded render commands and input events are available for test assertions.
🎯 Why this matters for TUI: A future TUI adapter must honor the render lifecycle if it implements this provider. That does not determine how it represents controls, focus, pointer input, or terminal output.

Why the Previous TUI Attempt Failed (Architecture-Level Analysis)

The discarded prototype exhibited several observed failures. They are evidence for requirements, not proof of a particular root cause:

  • Constant flickering: The next scope must define visually stable output during idle and normal interaction.
  • Non-functional controls: Every included interactive control needs defined keyboard and click behavior with a state-change test.
  • No mouse support: The first release now includes clicks; mouse movement and scrolling are explicitly out of scope.
  • Unpredictable tab focus: Tab and Shift+Tab must have deterministic transitions across enabled controls.
⚠️ The current boundary: IUserInterfaceProvider has no members. It therefore cannot currently express portable UI controls, focus, pointer events, layout, invalidation, or resizing. The next design must define those observable requirements before adding shared contract members.
  • Do not assume that graphical draw commands should become terminal controls.
  • Do not assume a TUI capability profile until the supported behavior is agreed.
  • Use capability metadata only for features defined by the current contract.

✅ Check Your Understanding

Answer each question from memory, then expand it to check your answer.

Why should game logic avoid directly using MonoGame APIs?

Direct use couples the game logic to MonoGame and prevents the same logic from running through another adapter without rewriting those calls.

What does IEngineAdapter represent?

It is the root adapter contract: it provides lifecycle methods, capabilities, and access to the focused engine providers.

Why are providers separate?

Each provider owns one focused responsibility, such as rendering, input polling, asset caching, or audio playback.

What does Capabilities tell game logic?

It advertises supported rendering, audio, and rich-UI features, plus contract and resource limits that the consumer can use to adapt its behavior.

What is the current render-frame sequence?

BeginFrame, submit draw commands, EndFrame, then Present. The render provider owns this sequence.

What did the discarded TUI attempt reveal?

The existing contracts do not define portable UI controls, focus, pointer events, layout, invalidation, or resizing. Those requirements must be agreed before implementation.
