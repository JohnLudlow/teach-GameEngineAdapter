Lesson 2: Contract Boundaries and Frame Lifecycle

Trace the real render contract before designing a TUI adapter.

Mission connection: The discarded TUI prototype showed why assumptions about rendering and UI behavior are dangerous. This lesson gives you one reliable habit: identify the contract that owns a behavior, then follow its explicit lifecycle.

One root adapter, several focused providers

IEngineAdapter is the composition root. It exposes adapter lifecycle methods, capabilities, and provider properties. It does not declare frame methods. The rendering contract belongs to IRenderProvider.

IEngineAdapter
├── Capabilities
├── InitializeAsync / ShutdownAsync
├── RenderProvider
├── InputProvider
├── UserInterfaceProvider
├── AssetProvider
└── AudioPlayer

This separation is useful because each provider has a narrow responsibility. For example, IInputProvider polls key, mouse-button, and mouse-position state; IAudioPlayer starts, stops, and adjusts playback; and IAssetProvider owns caching and delegates loading to an asset loader.

The render frame is an explicit sequence

The source defines this sequence for each render frame:

1. Begin: call BeginFrame(in camera).
2. Submit: call zero or more SubmitSprite, SubmitText, or SubmitMesh methods.
3. End: call EndFrame().
4. Present: call Present() to make the frame visible.
Important: FrameScope.Dispose() intentionally does nothing. A using declaration marks the active scope, but it does not replace EndFrame() or Present(). Omitting either method is a contract error.

The headless deterministic runner demonstrates the intended ordering:

using var scope = renderProvider.BeginFrame(in camera);
onTick?.Invoke(context);
renderProvider.EndFrame();
renderProvider.Present();

That runner advances simulated time only after Present(). This makes the ordering observable in deterministic tests.

What this means for TUI work

The current IUserInterfaceProvider is empty. It does not define controls, focus traversal, pointer events, layout, invalidation, or resizing. A TUI cannot gain portable checkbox interaction or deterministic Tab behavior merely by implementing the empty interface.

That is not a request to add a contract yet. It is an evidence-based boundary: first write observable requirements for the first TUI controls, input behavior, focus order, redraw strategy, and resize behavior. Then decide which shared contract is needed.

Retrieval practice

Answer each question from memory, then expand it to check your answer. Exact interface and method names matter when you trace behavior.

Which interface owns BeginFrame, EndFrame, and Present?

IRenderProvider.

Does disposing FrameScope present the frame?

No. Disposal is intentionally a no-op; the caller must explicitly call EndFrame and Present.

Which current provider has no members and therefore defines no portable UI interaction model?

IUserInterfaceProvider.
