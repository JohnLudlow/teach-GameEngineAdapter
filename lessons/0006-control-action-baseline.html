Lesson 6: Control Action Baseline

Define how first-release controls respond without coupling those responses to game-specific actions.

Mission connection: The first TUI can now promise concrete interaction behavior for each interactive control. This closes the “non-functional controls” gap without assuming what the game should do when an action occurs.

Shared rules remain in force

These control actions build on the focus baseline: Tab and Shift+Tab traverse enabled eligible controls deterministically; a click first moves focus to an enabled interactive control; and disabled controls retain focus but cannot activate. The tables below define what activation means for each control.

Checkbox

Input Required transition Visible result
Space or Enter while focused Toggle the checked state once. The next render shows the new checked state.
Click while enabled Focus the checkbox, then toggle its checked state once. The next render shows both focus and the new checked state.

List

Input Required transition Visible result
Up or Down while focused Change the selected item according to the list's bounds rule. The next render marks the new selected item.
Space or Enter while focused Activate the selected item once. The consumer receives one activation event for that selected item.
Remaining list decision: the current baseline does not define whether Up at the first item or Down at the last item wraps, clamps, or does nothing. That is a required follow-up before implementation.

Button

Input Required transition Visible result
Space or Enter while focused Invoke the assigned action exactly once. The consumer receives one invocation and controls the resulting application state.
Click while enabled Focus the button, then invoke its assigned action exactly once. The consumer receives one invocation and the next render reflects its resulting state.

Tab control

Input Required transition Visible result
Left or Right while focused Change the selected page according to the tab control's bounds rule. The next render marks the selected tab and shows its page.
Click a tab while enabled Focus the tab control and select the clicked page. The next render marks the clicked tab and shows its page.
Space or Enter while focused Activate the selected page once. The consumer receives one page-activation event.

Separate shared mechanics from domain effects

The adapter can deterministically report a checkbox toggle, selected-list-item activation, button invocation, or tab-page activation. It must not infer the game’s domain effect. For example, a button could open a menu, save configuration, or start a turn; the consumer owns that decision.

Given: focus is on "save-button"
When: Enter is pressed
Then: "save-button" invokes its assigned action once

Given: focus is on "faction-list" with "Romans" selected
When: Space is pressed
Then: the consumer receives one activation for "Romans"

Retrieval practice

Answer each question from memory, then expand it to check your answer.

Which three inputs toggle an enabled checkbox?

Space, Enter, and click. A click first moves focus to the checkbox, then toggles it once.

What do Space and Enter do for a focused list?

They activate the selected item once. Up and Down change which item is selected.

What do Left and Right do for a focused tab control?

They change the selected page. The tab control's bounds behavior still needs a decision.

Why should the adapter not decide what an activated button does in the game?

The button's domain effect belongs to the consumer. The shared contract should report the portable invocation event without assuming an application-specific result.
