Lesson 1: Architecture Overview

Understanding the adapter pattern, provider model, and how GameEngineAdapter decouples game logic from engines

📖 Lesson Goal: Understand the architectural patterns that make GameEngineAdapter work. By the end, you'll be able to explain why it's organized the way it is, and what each layer does.

The Problem: Coupling Game Logic to Engine-Specific Code

Imagine you're writing a 4X game in MonoGame. You write:

// Game logic tied to MonoGame
class GameSimulation
{
    private SpriteBatch _spriteBatch;  // MonoGame-specific
    private Keyboard _keyboard;         // MonoGame-specific

    public void Update()
    {
        // Your game logic is now hardcoded to MonoGame APIs
        _spriteBatch.Draw(...);
    }
}

Now you want to run the same game on Stride, or in a Terminal UI, or in a Headless test environment. Problem: your entire game logic is entangled with MonoGame. You have to rewrite everything.

GameEngineAdapter solves this by inverting the dependency: your game logic depends on abstract contracts (interfaces), not concrete engine code. Each engine implements the contracts. Game logic stays portable.

The Solution: The Adapter Pattern

GameEngineAdapter uses the Adapter Pattern (also called Hexagonal Architecture or Ports and Adapters):

    ┌──────────────────────────────────┐
    │        GAME LOGIC                │
    │      (Your 4X Game)              │
    └──────────────┬───────────────────┘
                   │
            ┌──────▼─────────┐
            │ IEngineAdapter │
            └──────┬─────────┘
                   │
        ┌──────────┼──────────┐
        │          │          │
    ┌───▼──┐  ┌────▼────┐  ┌──▼────────┐
    │Render│  │ Input   │  │  Audio    │
    │      │  │         │  │           │
    │ Prov │  │ Prov    │  │ Player    │
    └──────┘  └─────────┘  └───────────┘
        │          │            │
    ┌───┴──────────┴────────────┴──┐
    │     (Multiple impls; each    │
    │     adapter picks which      │
    │     providers to support)    │
    │                              │
    │   • MonoGame                 │
    │   • Stride                   │
    │   • TUI                      │
    │   • Headless                 │
    └──────────────────────────────┘
Key insight: Game logic sits at the center, depending only on abstract IEngineAdapter and its providers. Each engine (MonoGame, TUI, Headless) implements these interfaces. Your game logic never changes.

The Three Architectural Layers

Layer Contains Location Dependencies
Core Contracts Interfaces (IEngineAdapter, IRenderProvider, etc.) and DTOs (SpriteDrawDto, etc.) GameEngineAdapter.Core/ None (no external deps)
Game Logic Your 4X game simulation Your project Depends on GameEngineAdapter.Core
Adapters Engine-specific implementations (MonoGame, TUI, Headless, etc.) GameEngineAdapter.Headless/, future adapters Depends on GameEngineAdapter.Core and engine libraries

The flow is always one direction: Game Logic → Contracts ← Adapters. Game logic never knows about adapters. Adapters depend on contracts.

The Central Contract: IEngineAdapter

Every engine adapter implements IEngineAdapter. It looks roughly like this:

public interface IEngineAdapter : IDisposable
{
    // Describe what this adapter can do
    EngineCapabilities Capabilities { get; }

    // Lifecycle
    Task InitializeAsync(EngineConfig config, CancellationToken ct = default);
    Task ShutdownAsync(CancellationToken ct = default);

    // Get providers for rendering, input, audio, assets, UI
    IRenderProvider RenderProvider { get; }
    IInputProvider InputProvider { get; }
    IAudioPlayer AudioPlayer { get; }
    IAssetProvider AssetProvider { get; }
    IUserInterfaceProvider UserInterfaceProvider { get; }

    // Frame lifecycle
    FrameScope BeginFrame();
    void EndFrame();
}

Each adapter must provide:

  • Capabilities — What features does this engine support? (2D, 3D, audio, text-only?)
  • Lifecycle methods — Initialize, shutdown, frame begin/end
  • Providers — Objects your game uses to render, receive input, play audio, manage assets, show UI

The Provider Model: Separation of Concerns

Rather than cramming everything into one mega-interface, GameEngineAdapter splits functionality into focused providers:

Provider What It Does Example Usage
IRenderProvider Submit draw commands (sprites, meshes, text) renderProvider.DrawSprite(sprite)
IInputProvider Receive keyboard, mouse, gamepad input inputProvider.GetKeyboardState()
IAudioPlayer Play, stop, and control audio audioPlayer.PlayAsync(sound)
IAssetProvider Load, cache, and manage game assets assetProvider.GetAssetAsync(id)
IUserInterfaceProvider Render UI elements (buttons, panels, text) uiProvider.SubmitElement(panel)

Why separate providers? Because a TUI adapter might not support IRenderProvider (no sprite rendering). But it should still support IUserInterfaceProvider (text panels and buttons). By splitting concerns, adapters can support what makes sense for their engine.

Capability Negotiation: Knowing What the Engine Can Do

Not all engines are equal. A Headless adapter can't render graphics. A TUI can't play audio. How does your game know?

Every adapter reports its EngineCapabilities:

public class EngineCapabilities
{
    public bool Supports2D { get; set; }      // Sprites, 2D transforms
    public bool Supports3D { get; set; }      // Meshes, 3D transforms
    public bool SupportsAudio { get; set; }   // Audio playback
    public bool SupportsText { get; set; }    // Text rendering
    public string ContractVersion { get; set; }
}

Your game logic checks capabilities and adapts:

void Render(IEngineAdapter adapter)
{
    if (adapter.Capabilities.Supports2D)
    {
        adapter.RenderProvider.DrawSprite(...);
    }
    else if (adapter.Capabilities.SupportsText)
    {
        adapter.UserInterfaceProvider.SubmitTextPanel(...);
    }
}

This way, the same game logic can adapt to different engines without conditional compilation or runtime errors.

A Concrete Example: The Frame Cycle (How HeadlessAdapter Works)

Let's trace a single frame through the HeadlessAdapter to see how these pieces fit together:

1. Game calls BeginFrame()
Returns a FrameScope — a disposable that marks the frame boundary.
2. Game processes input
inputProvider.GetKeyboardState() returns queued keyboard events. In Headless, this is pre-recorded test data.
3. Game updates simulation
Game logic runs. Calls audioPlayer.PlayAsync(...), assetProvider.GetAssetAsync(...), etc.
4. Game submits render commands
renderProvider.DrawSprite(dto), renderProvider.DrawText(dto), etc. In Headless, these are recorded (not actually rendered).
5. Game disposes FrameScope
Disposing triggers EndFrame(). Adapter finishes the frame (swaps buffers, clears state, etc.).
✅ Frame complete. Recorded render commands and input events are available for test assertions.
🎯 Why this matters for TUI: The frame cycle is the same regardless of engine. A TUI adapter would follow the exact same cycle — it just renders to the terminal instead of a graphics buffer, and reads input from the terminal instead of a gaming console.

Why the Previous TUI Attempt Failed (Architecture-Level Analysis)

The previous TUI implementation had several classic failures:

  • Constant flickering: Likely tried to re-render IRenderProvider.DrawSprite() commands to ASCII art every frame. Terminal rendering is expensive; flickering indicates no dirty-region tracking or double-buffering.
  • Non-functional controls: UI elements (checkboxes) weren't responding. Probably because the TUI tried to implement controls within the adapter, rather than delegating to IUserInterfaceProvider.
  • No mouse support: Mouse events require event-based input architecture. The TUI may have tried polling or buffering incorrectly.
  • Unpredictable tab focus: Tab/focus management is not a terminal-native feature. Had to be manually implemented and likely was done incorrectly.
⚠️ The core issue: TUI is fundamentally different from graphical rendering. A TUI can't efficiently map IRenderProvider calls (sprites, meshes, transforms) to terminal output. A better design would be:
  • TUI reports Supports2D = false, Supports3D = false (not a graphics engine)
  • All TUI output goes through IUserInterfaceProvider (text panels, buttons, grids)
  • Game logic checks capabilities and renders differently for TUI
